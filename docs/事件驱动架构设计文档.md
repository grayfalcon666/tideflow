## 1. 拓扑总览

| Exchange | 类型 | Binding Key | Routing Key | 用途 |
|---|---|---|---|---|
| video.events | topic | video.publish | video.publish | 视频发布（全局时间线 + Outbox + Inbox 推送） |
| like.events | topic | like.* | like.like / like.unlike | 点赞/取消点赞 |
| comment.events | topic | comment.* | comment.publish / comment.delete | 评论发布/删除 |
| social.events | topic | social.* | social.follow / social.unfollow | 关注/取关 |
| video.popularity.events | topic | video.popularity.* | video.popularity.update | 热度增量更新（Redis 窗口） |
| dlx.events | topic | # | - | 死信队列 |

所有队列均配置 `x-dead-letter-exchange: dlx.events`，消费失败 Nack 后进入 DLX，最多重试 3 次。  
消息持久化、队列持久化、Manual Ack 等可靠性机制保持不变。

## 2. 视频发布事件（video.publish）

**Routing Key**：`video.publish`

**消息结构**：
```
VideoPublishEvent{
    EventID,
    VideoID,
    AuthorID,
    CreateTime (UnixMilli),
    OccurredAt
}
```

**生产者**：`OutboxWorker` 轮询 `outbox_msgs` 表，发布至 `video.publish`。

**消费者**：`TimelineWorker`（原 `StartConsumer` 内消费，部署于 API Server 进程）
1. **写全局时间线**：`ZADD v1:feed:global {videoID} {createTime}`，`ZREMRANGEBYRANK` 保留 1000 条（可选，按产品需要开启）。
2. **写作者发件箱**：`ZADD v1:outbox:{AuthorID} {videoID} {createTime}`，`ZREMRANGEBYRANK` 保留 5000 条。
3. **Inbox 推送判断**：
   - 读取 `accounts` 表 `follower_count` 或 Redis 缓存的大 V 标记。
   - 若 `follower_count` < 阈值（默认 10000），则**异步批量推送**至该博主所有粉丝的收件箱：
     - 从 `socials` 表分页获取粉丝列表（每次 500 条）。
     - 对每个粉丝执行 `ZADD v1:inbox:{fanID} {videoID} {createTime}`，`ZREMRANGEBYRANK` 保留 1000 条。
   - 若为大 V，仅写发件箱，**不推送**粉丝 Inbox。
4. **失效缓存**（可选）：删除作者的冷拉取缓存 `v1:feed:followcache:{authorID}:*` 键，保证数据新鲜度。

**优化**：  
- 大 V 判定可使用 `accounts.follower_count` 或本地缓存，避免频繁 DB 查询。  
- Inbox 推送可拆分为独立队列（如 `video.inbox.push`），由专用 Worker 处理，防止阻塞核心时间线写入。当前设计先在一体化 Worker 中实现，若粉丝量极大可后续拆分。

## 3. 点赞事件（like.like / like.unlike）

**Routing Keys**：`like.like`、`like.unlike`

**消息结构**：
```
LikeEvent{
    EventID,
    Action  ("like" / "unlike"),
    UserID,
    VideoID,
    OccurredAt
}
```

**生产者**：`LikeService.Like()` / `Unlike()`

**消费者**：`LikeWorker`  
- **applyLike**：`LikeIgnoreDuplicate`（幂等）→ `ChangeLikesCount(+1)` + `ChangePopularity(+1)`（若有热度公式则合并更新）
- **applyUnlike**：`DeleteByVideoAndAccount` → `ChangeLikesCount(-1)` + `ChangePopularity(-1)`

同时，消息会由 **NotificationWorker** 消费（共用同一 Exchange，不同队列绑定 `like.like`），写入 `notifications` 表并 SSE 推送。

---

## 4. 评论事件（comment.publish / comment.delete）

**Routing Keys**：`comment.publish`、`comment.delete`

**消息结构**：
```
CommentEvent{
    EventID,
    Action  ("publish" / "delete"),
    CommentID,
    Username,
    VideoID,
    AuthorID,
    Content,
    OccurredAt
}
```

**生产者**：`CommentService.Publish()`

**消费者**：`CommentWorker`  
- **applyPublish**：写入 `comments` 表 → `ChangePopularity(+评论权重)`
- **applyDelete**：软删除评论，**需补充减少 popularity 逻辑**（原缺陷修复）

`NotificationWorker` 监听 `comment.publish`，生成通知并推送。

## 5. 关注/取关事件（social.follow / social.unfollow）

**Routing Keys**：`social.follow`、`social.unfollow`

**消息结构**：
```
SocialEvent{
    EventID,
    Action  ("follow" / "unfollow"),
    FollowerID,
    VloggerID,
    OccurredAt
}
```

**生产者**：`SocialService.Follow()` / `Unfollow()`

**消费者**：`SocialWorker`  
- **Follow**：插入 `socials` 表（重复 1062 静默忽略）→ **更新博主 `follower_count`**（`accounts.follower_count ± 1`）  
  此处改为通过 MQ 异步更新 `follower_count`，避免事务耦合，可接受最终一致。
- **Unfollow**：删除记录 → 同样更新 `follower_count`。

`NotificationWorker` 监听 `social.follow`，生成通知并推送。

> **重要修改**：以前直接写 MySQL `socials` 表而不更新计数，现在需在关注/取关时联动更新 `accounts.follower_count`，用于后续推拉策略的大 V 判定。

## 6. 热度增量事件（video.popularity.update）

**Routing Key**：`video.popularity.update`

**消息结构**：
```
PopularityEvent{
    EventID,
    VideoID,
    Change  (增量值，如+1),
    OccurredAt
}
```

**生产者**：`VideoService.UpdatePopularity()`，在 `likes_count` 或 `popularity` 写入后，通过 MQ 异步更新 Redis 热门窗口。

**消费者**：`PopularityWorker`  
- 执行 `ZINCRBY v1:hot:video:1m:{YYYYMMDDHHmm} {videoID} {change}`  
- 若成功，依靠时间窗口 TTL 实现衰减；若失败 Nack 重试。

---

## 7. 通知队列（Notification）

沿用原有设计：三个队列分别绑定 `like.like`、`comment.publish`、`social.follow`，与业务 Worker 共享同一个 Exchange，但绑定到不同 Queue。  
`NotificationWorker`（内嵌于 API 进程）消费后写入 `notifications` 表，并通过 `SSEHub.Push` 实时推送给用户。

## 8. 全链路数据流

### 8.1 视频发布
```
用户 POST /publish
  → 事务写入 videos + outbox_msgs
  → OutboxWorker 轮询 outbox_msgs，发布 video.publish 消息
  → TimelineWorker 消费：
      1. ZADD v1:feed:global (可选)
      2. ZADD v1:outbox:{authorID}
      3. 判断大V：
         - 普通博主 → 遍历粉丝 ZADD v1:inbox:{fanID}，裁剪至1000
         - 大V → 仅写Outbox
```

### 8.2 互动（点赞 / 评论 / 关注）
```
用户操作
  → Service 同步写 MySQL (幂等)
  → 异步发 MQ
       ├─ 业务Worker：修改 counts / popularity / socials
       ├─ PopularityWorker：ZINCRBY 热度窗口
       └─ NotificationWorker：通知持久化 + SSE推送
```

### 8.3 读取 Feed（无 MQ 参与）
```
GetUserFeed (HTTP)
  → Redis: 并行读 v1:inbox:{uid} + v1:outbox:{大Vids}
  → 合并排序
  → GetVideoByIDs (三级缓存)
  → 若遇冷边界 → 拉模式构建冷缓存 (singleflight + 分布式标记)
```

### 划分原则
|链路|一致性要求|失败后果|模式|
|---|---|---|---|
|视频发布|强一致|视频不可见，体验致命|**Outbox**|
|点赞/评论/关注|最终一致|计数短暂偏差，可自愈|**直接发 MQ**|
|通知推送|允许偶尔丢失|通知延迟或缺失，非致命|**直接发 MQ**
